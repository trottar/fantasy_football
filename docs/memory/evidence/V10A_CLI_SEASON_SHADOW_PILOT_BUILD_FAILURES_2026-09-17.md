# v1.0A CLI + Season Shadow-Pilot Build Failures

<!-- FANTASY_EVIDENCE_V10A_CLI_SEASON_SHADOW_BUILD_FAILURES_20260917:BEGIN -->
## Pre-delivery artifact/QA failures

1. While hardening the pilot so observability import failures fall back to the
   original uninstrumented behavior, the first assistant-side package-edit
   script used conflicting nested triple-quote delimiters and raised
   `SyntaxError` before it executed.
2. The first accumulated-suite reconstruction invoked the standalone `pytest`
   executable, which did not inherit the reconstructed repository import path;
   rerunning with the project validation convention `python -m pytest` fixed the
   harness issue.
3. The next reconstructed integration-plan test failed because the synthetic QA
   tree omitted placeholder production source paths required by the existing
   plan-source existence test. Adding only those path fixtures produced the
   expected 79/79 accumulated pre-pilot pass.
4. The delivered v1 pilot package failed on the user's Windows machine before
   modification at `verify_local_matches_prestate()` because it required
   `L:\Projects\fantasy_football\fantasy.py`. The commissioned release
   layout never placed the runnable application directly at that control root;
   the v0.36-repack1 installer defines the runnable tree as
   `fantasy_season_v0_36_repack1`. The v1 pilot therefore conflated the
   checkpoint/control root with the installed release tree.
5. While constructing the v2 successor, two assistant-side package-edit scripts
   used conflicting Python string delimiters and raised `SyntaxError` before
   executing.
6. The first accumulated-suite v2 reconstruction used a synthetic
   `SeasonGuiService` initializer annotation that did not match the exact
   predecessor anchor. The installer correctly rejected that QA fixture. Because
   that shell harness was not using `set -e`, pytest then ran against the
   partially patched synthetic tree and produced two follow-on test failures.
   Rebuilding the fixture with the exact replacement anchor and fail-fast shell
   semantics produced a clean 90/90 pass.
7. The downloaded v2 ZIP failed on the user's Windows machine in PowerShell
   `Expand-Archive` with `Central Directory corrupt` before extraction. The
   source-side v2 archive retained by the assistant independently matched its
   reported SHA-256 and byte count and passed Python `ZipFile.testzip()` plus
   `unzip -t`; therefore this incident is classified as a delivered/archive
   transport failure rather than an installer execution or project-state
   failure. The inner PowerShell script did not exist because extraction never
   completed.

Items 1-3, 5, and 6 are classified:
`FAILED DURING ARTIFACT CONSTRUCTION/QA / BEFORE DELIVERY / NO PROJECT
MODIFICATION`.

Item 4 is classified:
`INVALID / SUPERSEDED / FAILED BEFORE MODIFICATION`.

Item 7 is classified:
`SUPERSEDED DELIVERY / FAILED BEFORE EXTRACTION / NO PROJECT MODIFICATION`.

8. The v3 self-contained launcher reconstructed and validated its embedded ZIP,
   identified GitHub main correctly, and then failed before modification in
   `verify_control_prestate()` because that verifier compared local
   `docs/memory/**` working-tree bytes to a fresh clone's checked-out working-tree
   bytes. The prior successful integration-gate installer had rewritten
   `CURRENT.md` with LF and copied that file directly into the control root,
   while a fresh Windows checkout may represent the same committed text with
   CRLF. The guard therefore treated a representation-only LF/CRLF difference as
   project drift.

Item 8 is classified:
`INVALID PRESTATE GUARD / FAILED BEFORE MODIFICATION / NO PROJECT MODIFICATION`.

9. The v4 machine-state preflight passed the corrected Git-object/control/runtime
   identity checks. The subsequent apply patched only the isolated staging clone,
   then failed before repository commit/push or local synchronization when
   `tools/probe_shadow_pilot.py` raised
   `ModuleNotFoundError: No module named 'fantasy'`. The probe was launched as a
   script under `tools/`, so Python placed that directory at `sys.path[0]`; the
   installer had not explicitly restored the repository/application root on
   `PYTHONPATH`. The application source itself was present and unchanged.

Item 9 is classified:
`INVALID PROBE EXECUTION CONTEXT / FAILED BEFORE MODIFICATION / NO PROJECT
MODIFICATION`.

10. During v5 pre-delivery QA, the accumulated observability suite passed 90/90,
    but a follow-on payload-identity assertion compared the entire historical v4
    payload directory to the clean v5 payload directory. The v4 directory
    contained local `__pycache__/*.pyc` artifacts generated by prior QA, while
    v5 intentionally contained only the three source/test/probe payload files.
    The assertion therefore failed on QA-directory contamination rather than a
    payload source difference. The comparator was narrowed to the explicit
    payload allowlist and QA was rerun from a clean tree.

Item 10 is classified:
`PRE-DELIVERY QA COMPARATOR DEFECT / NO PROJECT MODIFICATION`.

11. The first v5 end-to-end offline preflight harness created its synthetic bare
    Git remote from a fixture repository whose default branch was `master`.
    The real installer intentionally queries `refs/heads/main`, so the harness
    failed immediately with `Remote branch missing` before exercising v5
    preflight logic. The fixture was rebuilt with an explicit `main` branch and
    the end-to-end preflight was rerun.

Item 11 is classified:
`PRE-DELIVERY QA FIXTURE DEFECT / NO PROJECT MODIFICATION`.

12. After the end-to-end apply simulation passed, the first invocation of the
    package's static-global audit helper omitted its required file arguments.
    The helper correctly printed usage and exited with code 2. The audit was
    immediately rerun with the installer and all three payload Python files and
    passed.

Item 12 is classified:
`PRE-DELIVERY QA INVOCATION ERROR / NO PROJECT MODIFICATION`.

13. The first final-packaging call attempted to delete a generated package
    `__pycache__` directory owned by the container runtime. The cleanup raised
    `PermissionError` before ZIP or launcher creation. The successor packaging
    path was changed to construct the archive from an explicit eight-file
    allowlist and to exclude cache artifacts without depending on deleting them.

Item 13 is classified:
`FAILED DURING ARTIFACT CONSTRUCTION / BEFORE DELIVERY / NO PROJECT MODIFICATION`.

For items 4, 7, 8, and 9, no repository commit/push or local runtime/control
synchronization occurred. GitHub remained at the integration-gate predecessor.
Items 10 through 13 occurred assistant-side before delivery.

Corrective rules:
- application-source installers must treat the control/checkpoint root and
  commissioned runnable release tree as distinct authorities;
- delivery archives used on Windows must be externally byte-verified before
  extraction when a prior transport/archive failure has occurred;
- pre-state validation must compare local working-tree text to committed Git
  object content with only line-ending representation normalized. It must never
  compare two independently checked-out working-tree byte streams as though they
  were the same authority layer;
- every runtime probe must execute under an explicit application import context,
  with the staged/runtime application root on `PYTHONPATH`; running a script from
  `tools/` is not equivalent to launching the application from its root;
- preflight must exercise the isolated staged patch and the real paired runtime
  probe before it may report `PASS`.

The v5 successor keeps the runtime-layout, Git-object identity, and delivery
hardening, and adds an explicit application execution environment plus a
preflight staged-patch/runtime-probe gate. The exact v4 import failure is
reproduced as a negative self-test and the corrected context is required to pass.
